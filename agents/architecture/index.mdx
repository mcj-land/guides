An agent is an LLM in a loop: it reads the request, decides what to do, calls tools, looks at the results and repeats until it can answer. Everything else in the architecture exists to run that loop reliably for many users at once.

## The big picture

| Part | Job |
|---|---|
| [API](/agents/architecture/api) | Accepts requests, authenticates, returns or streams the answer |
| [Runtime](/agents/architecture/runtime) | Picks the agent and runs its loop behind one common interface |
| [Model gateway](/agents/architecture/model-gateway) | One way to call any LLM, with retries, fallbacks and limits |
| [Tools](/agents/architecture/tools) | The actions an agent can take in other systems |
| [Memory](/agents/architecture/memory) | Conversation history and long-term knowledge |
| [Prompts](/agents/architecture/prompts) | Instructions, versioned outside the code |
| [Observability](/agents/architecture/observability) | Traces, cost and quality of every run |

## Why split it this way

Each part changes for a different reason. Models change every few months, tools change when you integrate a new system, and prompts change daily. Keeping them behind separate interfaces means you can swap one without touching the others. New agents then only bring their own prompt and tools, and reuse the rest.
