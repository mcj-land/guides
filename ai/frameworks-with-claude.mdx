This page shows how to steer Claude Opus 5.5 (`claude-opus-5-5`) toward each framework in this section: [HIPA](/ai/hipa), [Chain-of-Thought](/ai/chain-of-thought), [Self-Consistency](/ai/self-consistency), [Tree of Thoughts](/ai/tree-of-thoughts), [ReAct](/ai/react), [Plan-and-Solve](/ai/plan-and-solve) and [Reflexion](/ai/reflexion).

Examples use the Python SDK (`pip install anthropic`). To use the frameworks in a normal chat, without code, see [Use frameworks in the chat](/ai/frameworks-in-chat).

## How Opus 5.5 reasons by default

Opus 5.5 always thinks before it answers. This internal reasoning is called **adaptive thinking**: the model decides how much to think for each request. You can't turn it off, and you don't set a token budget for it.

This changes the role of the frameworks. Most were designed for models that did *not* think on their own. With Opus 5.5, you don't use a framework to make the model reason. You use it to decide:

- **How much** it reasons: the `effort` setting.
- **What shape** the work and the answer take: the system prompt and the output format.
- **What happens around the model**: several calls, tools, evaluators and retries in your code.

## The three levers

| Lever | What it controls | Where you set it |
|---|---|---|
| Effort | Depth of internal thinking, latency and cost | `output_config={"effort": ...}` with `low`, `medium`, `high`, `xhigh` or `max`. The default is `medium`, so set it explicitly |
| Prompt | Which stages to follow and how to structure the answer | `system` prompt, user message, `output_format` for structured output |
| Harness | Multiple calls, voting, search, tools, feedback loops | Your Python code |

Each framework needs a different mix:

| Framework | Effort | Prompt | Harness |
|---|---|---|---|
| HIPA | `medium` to `high` | Main lever: the four stages and the answer structure | Optional: one component per stage |
| Chain-of-Thought | Main lever: raise it for harder problems | Ask for a short explanation, not the full reasoning | None |
| Self-Consistency | `low` to `medium` per sample | Same task, different approach per sample | Main lever: N calls and a vote |
| Tree of Thoughts | `low` for proposals and scoring | Separate propose and evaluate prompts | Main lever: the search loop |
| ReAct | `medium` | Say when to use each tool | Main lever: tools and the agent loop |
| Plan-and-Solve | `high` for the planner, `low` to `medium` for steps | Plan first, then execute | Optional: planner and executor calls |
| Reflexion | `medium` | Actor and reflection prompts | Main lever: evaluator and retry loop |

## Rules for Opus 5.5

Some older prompting habits fail or backfire on Opus 5.5:

| Don't | Do instead |
|---|---|
| Write "think step by step" or "show all your reasoning in the answer" | The model already thinks. Raise `effort`. Ask for a *short* explanation of the answer. A prompt that asks the model to reproduce its internal reasoning can be declined (`stop_details.category: "reasoning_extraction"`) |
| Send `thinking={"type": "disabled"}` or a `budget_tokens` value | Omit `thinking`. Use `effort="low"` for fast answers. Both return a 400 error |
| Set `temperature`, `top_p` or `top_k` | Sampling parameters are not supported. Get variety by changing the prompt |
| Force a tool with `tool_choice={"type": "tool", ...}` or `{"type": "any"}` | Use `tool_choice={"type": "auto"}`, name the tool in the prompt and set `strict: True` on the tool. Check that the call happened |
| Prefill the start of the assistant answer | Use structured outputs (`output_format`) or system prompt instructions |
| Edit or delete earlier messages in a running conversation | Append new messages only. Editing history invalidates earlier thinking blocks |

To read the model's reasoning yourself, for debugging, ask for a summary of it with `thinking={"type": "adaptive", "display": "summarized"}`. It arrives in `thinking` blocks, separate from the answer.

## Base request

All examples below use this helper. It sets effort explicitly, turns on server-side fallbacks so a safety-classifier refusal is retried on another model, and returns only the text blocks.

```python
import anthropic

client = anthropic.Anthropic()
MODEL = "claude-opus-5-5"


def ask(system: str, user: str, effort: str = "medium", max_tokens: int = 16000) -> str:
    response = client.beta.messages.create(
        model=MODEL,
        max_tokens=max_tokens,  # leave room for thinking: it counts toward max_tokens
        system=system,
        output_config={"effort": effort},
        betas=["server-side-fallback-2026-07-01"],
        fallbacks="default",
        messages=[{"role": "user", "content": user}],
    )
    if response.stop_reason == "refusal":
        raise RuntimeError(f"Declined: {response.stop_details}")
    return "".join(block.text for block in response.content if block.type == "text")
```

<Note>
Server-side fallbacks work on the Claude API and Claude Platform on AWS. On Amazon Bedrock, Google Vertex AI and Microsoft Foundry, use the SDK's client-side fallback middleware instead.
</Note>

## HIPA

HIPA is mostly a prompt framework. Describe the four stages in the system prompt and ask for an answer whose sections match them. The sections are part of the deliverable, so you are not asking for the model's internal reasoning.

```python
HIPA_SYSTEM = """You are a decision-support assistant. Structure every answer in four sections:

## Understanding
The request in your own words, the user's goal, constraints, and any assumptions you made.

## Relevant facts
The facts from the provided context that matter for this decision. Mark anything uncertain.

## Options and criteria
At least two realistic options. The criteria you used (cost, risk, effort, user impact)
and how each option scores against them.

## Recommendation
Your recommendation first, then the main trade-off, the next steps,
and what would change your recommendation.

Write for: {audience}."""

answer = ask(
    system=HIPA_SYSTEM.format(audience="a non-technical product manager"),
    user="We must choose between building our own search or using a managed service. Context: ...",
    effort="high",
)
```

For a pipeline, return the stages as structured data, so you can log and test each one:

```python
from pydantic import BaseModel


class Option(BaseModel):
    name: str
    scores: dict[str, int]  # criterion -> score from 1 to 5
    trade_offs: str


class HipaAnswer(BaseModel):
    understanding: str
    assumptions: list[str]
    relevant_facts: list[str]
    criteria: list[str]
    options: list[Option]
    recommendation: str
    next_steps: list[str]


response = client.messages.parse(
    model=MODEL,
    max_tokens=16000,
    system=HIPA_SYSTEM.format(audience="an engineering lead"),
    output_config={"effort": "high"},
    messages=[{"role": "user", "content": "..."}],
    output_format=HipaAnswer,
)
result = response.parsed_output
```

## Chain-of-Thought

With Opus 5.5, Chain-of-Thought is built in. Don't add "think step by step". Control the depth with `effort`, and ask for a short justification if the user needs one.

```python
answer = ask(
    system="Answer the question. After the answer, add a short explanation (3 bullets maximum) of how you got it.",
    user="A train leaves at 09:40 and the trip takes 2 h 55 min with a 25 min stop. When does it arrive?",
    effort="high",  # raise for harder problems, lower for simple ones
)
```

| Problem | Suggested effort |
|---|---|
| Simple fact or format conversion | `low` |
| Typical multi-step question | `medium` (default) |
| Hard math, logic or analysis | `high` |
| Correctness matters more than cost | `xhigh` or `max`, only after you measure a gain |

## Self-Consistency

You can't add randomness with `temperature` on Opus 5.5, so make the samples independent by giving each one a different approach. Then vote on a structured answer.

```python
from collections import Counter
from concurrent.futures import ThreadPoolExecutor

from pydantic import BaseModel


class FinalAnswer(BaseModel):
    answer: str  # normalized: a number, a label, yes/no


APPROACHES = [
    "Solve it algebraically.",
    "Solve it by working backwards from the result.",
    "Solve it by testing concrete values.",
    "Solve it by drawing a table of the quantities.",
    "Solve it by estimating first, then refining.",
]


def sample(problem: str, approach: str) -> str:
    response = client.messages.parse(
        model=MODEL,
        max_tokens=8000,
        system=f"{approach} Return only the final answer.",
        output_config={"effort": "low"},
        messages=[{"role": "user", "content": problem}],
        output_format=FinalAnswer,
    )
    return response.parsed_output.answer.strip().lower()


def self_consistency(problem: str) -> tuple[str, float]:
    with ThreadPoolExecutor() as pool:
        answers = list(pool.map(lambda a: sample(problem, a), APPROACHES))
    answer, votes = Counter(answers).most_common(1)[0]
    return answer, votes / len(answers)  # answer and agreement ratio
```

Before you build this, compare it with a single call at a higher effort. On Opus 5.5, one `high` call often matches several `low` samples at a lower cost. Keep Self-Consistency when you need the agreement ratio as a confidence signal.

## Tree of Thoughts

Use two prompts: one proposes candidate next steps, the other scores a partial solution. Both return structured output, so the search loop in your code stays simple.

```python
from pydantic import BaseModel


class Proposals(BaseModel):
    next_steps: list[str]


class Score(BaseModel):
    score: int  # 1 (dead end) to 10 (almost solved)
    reason: str


def propose(problem: str, state: str, n: int = 3) -> list[str]:
    response = client.messages.parse(
        model=MODEL,
        max_tokens=8000,
        system=f"Propose {n} different, promising next steps for the partial solution. Each step must be one short action.",
        output_config={"effort": "low"},
        messages=[{"role": "user", "content": f"Problem:\n{problem}\n\nPartial solution so far:\n{state or '(empty)'}"}],
        output_format=Proposals,
    )
    return response.parsed_output.next_steps[:n]


def evaluate(problem: str, state: str) -> int:
    response = client.messages.parse(
        model=MODEL,
        max_tokens=4000,
        system="Score how likely this partial solution is to lead to a correct, complete solution. Check it against every constraint of the problem.",
        output_config={"effort": "low"},
        messages=[{"role": "user", "content": f"Problem:\n{problem}\n\nPartial solution:\n{state}"}],
        output_format=Score,
    )
    return response.parsed_output.score


def tree_of_thoughts(problem: str, depth: int = 3, keep: int = 2) -> str:
    states = [""]
    for _ in range(depth):
        candidates = [f"{s}\n- {step}".strip() for s in states for step in propose(problem, s)]
        states = sorted(candidates, key=lambda c: evaluate(problem, c), reverse=True)[:keep]
    return states[0]
```

For a lighter version, ask for the exploration in one prompt: "List three different approaches, score each against the constraints, then develop only the best one."

## ReAct

ReAct is the native way Opus 5.5 uses tools. Give it the tools, say in the system prompt when to use each one, and run the agent loop. You don't need text markers such as `Thought:` or `Action:`: thinking happens internally, and tool calls arrive as `tool_use` blocks.

```python
tools = [
    {
        "name": "search_docs",
        "description": "Search the internal documentation. Returns the top matching passages with their URLs.",
        "strict": True,
        "input_schema": {
            "type": "object",
            "properties": {"query": {"type": "string"}},
            "required": ["query"],
            "additionalProperties": False,
        },
    },
]

SYSTEM = """Answer questions about our platform.
Use search_docs before you answer any question about features, limits or configuration.
Cite the URL of every passage you rely on. If the documentation doesn't answer the question, say so."""


def react(question: str, max_steps: int = 10) -> str:
    messages = [{"role": "user", "content": question}]
    for _ in range(max_steps):
        response = client.messages.create(
            model=MODEL,
            max_tokens=16000,
            system=SYSTEM,
            tools=tools,
            tool_choice={"type": "auto"},
            output_config={"effort": "medium"},
            messages=messages,
        )
        if response.stop_reason == "refusal":
            raise RuntimeError(f"Declined: {response.stop_details}")
        # Append the full content, including thinking blocks, unchanged
        messages.append({"role": "assistant", "content": response.content})
        if response.stop_reason != "tool_use":
            return "".join(b.text for b in response.content if b.type == "text")
        # Return all tool results in one user message
        results = [
            {"type": "tool_result", "tool_use_id": b.id, "content": run_tool(b.name, b.input)}
            for b in response.content
            if b.type == "tool_use"
        ]
        messages.append({"role": "user", "content": results})
    return "Stopped: step limit reached."
```

To skip writing the loop, use the SDK's tool runner (`client.beta.messages.tool_runner`). See also [Agent loop](/agents/architecture/agent-loop) and [Tools](/agents/architecture/tools).

## Plan-and-Solve

For a single call, ask for the plan as part of the answer. The plan is a deliverable the user can review, not the model's internal reasoning.

```python
PLAN_AND_SOLVE_SYSTEM = """Work in two parts.

## Plan
A numbered list of the steps needed to complete the task. Each step is one action.

## Execution
Carry out each step in order, under a heading with its number. Give the result of each step.
End with the final result."""

answer = ask(PLAN_AND_SOLVE_SYSTEM, "Prepare a migration checklist for moving our API from VMs to containers.", effort="high")
```

For long tasks, split the planner and the executor. Plan at high effort once, then run each step at a lower effort:

```python
from pydantic import BaseModel


class Plan(BaseModel):
    steps: list[str]


plan = client.messages.parse(
    model=MODEL,
    max_tokens=16000,
    system="Break the task into 3 to 8 ordered, independent steps. Each step must be executable on its own.",
    output_config={"effort": "high"},
    messages=[{"role": "user", "content": task}],
    output_format=Plan,
).parsed_output

results: list[str] = []
for i, step in enumerate(plan.steps, 1):
    context = "\n\n".join(results)
    results.append(ask(
        system="Execute only the step you are given. Use the previous results as context.",
        user=f"Task: {task}\n\nPrevious results:\n{context}\n\nStep {i}: {step}",
        effort="medium",
    ))

final = ask("Combine the step results into one final deliverable.", f"Task: {task}\n\n" + "\n\n".join(results))
```

## Reflexion

Reflexion needs an evaluator outside the model when possible: tests, a schema, rules. Feed the evaluator's feedback back as a new user message, so the conversation stays append-only.

```python
ACTOR_SYSTEM = "Write a Python function that solves the task. Return only the code."


def reflexion(task: str, max_attempts: int = 3) -> str:
    messages = [{"role": "user", "content": task}]
    code = ""
    for _ in range(max_attempts):
        response = client.messages.create(
            model=MODEL,
            max_tokens=16000,
            system=ACTOR_SYSTEM,
            output_config={"effort": "medium"},
            messages=messages,
        )
        messages.append({"role": "assistant", "content": response.content})
        code = "".join(b.text for b in response.content if b.type == "text")

        result = run_tests(code)  # your evaluator
        if result.passed:
            return code

        messages.append({
            "role": "user",
            "content": (
                f"The tests failed:\n{result.feedback}\n\n"
                "First, write two or three sentences on what went wrong and what you will change. "
                "Then write the corrected function."
            ),
        })
    return code  # best effort after the last attempt
```

Without tests, use a second call with a rubric as the evaluator. Use a separate system prompt for it, so it doesn't share the actor's blind spots.

## Let Opus 5.5 choose the framework

When requests vary, describe the frameworks in the system prompt and let the model pick one for each request. This works for the prompt-only frameworks (HIPA, Chain-of-Thought, Plan-and-Solve).

```python
ROUTER_SYSTEM = """Before you answer, pick the approach that fits the request:

- Decision or recommendation between options -> answer with the sections
  Understanding, Relevant facts, Options and criteria, Recommendation.
- Long task with several steps -> answer with a numbered Plan, then the Execution of each step.
- Calculation, logic or a direct question -> give the answer and a short explanation.

Start your answer with one line: "Approach: <decision | plan | direct>"."""
```

For the frameworks that need code (Self-Consistency, Tree of Thoughts, ReAct, Reflexion), classify the request first and route it in your harness:

```python
from typing import Literal

from pydantic import BaseModel


class Route(BaseModel):
    framework: Literal["hipa", "direct", "plan_and_solve", "self_consistency", "tree_of_thoughts", "react", "reflexion"]
    reason: str


route = client.messages.parse(
    model=MODEL,
    max_tokens=2000,
    system="""Classify the request:
- hipa: a decision between options that needs a justified recommendation
- direct: a question with one clear answer
- plan_and_solve: a long task with several steps
- self_consistency: a question with a short answer where confidence matters
- tree_of_thoughts: a puzzle or design problem where early choices block later ones
- react: needs live or internal data from tools
- reflexion: produces code or output that can be checked by tests or rules""",
    output_config={"effort": "low"},
    messages=[{"role": "user", "content": request}],
    output_format=Route,
).parsed_output

HANDLERS[route.framework](request)
```

## Choose a framework

| If the task... | Use | Opus 5.5 setup |
|---|---|---|
| Needs a justified recommendation for a person | [HIPA](/ai/hipa) | System prompt with the four sections, `high` effort |
| Is a hard question with one answer | [Chain-of-Thought](/ai/chain-of-thought) | Just raise `effort` |
| Needs a confidence score | [Self-Consistency](/ai/self-consistency) | N parallel calls with different approaches, vote |
| Has dead ends and needs exploration | [Tree of Thoughts](/ai/tree-of-thoughts) | Propose and evaluate calls, search loop |
| Needs live or private data | [ReAct](/ai/react) | Tools, `auto` tool choice, agent loop |
| Is long, with several steps | [Plan-and-Solve](/ai/plan-and-solve) | Plan in the answer, or planner and executor calls |
| Has a result you can check automatically | [Reflexion](/ai/reflexion) | Evaluator and append-only retry loop |

The frameworks combine well. A common setup is Plan-and-Solve to plan, ReAct to run each step and Reflexion to check the result.
